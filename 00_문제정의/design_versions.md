# 설계 비교: 파일 직접 읽기 방식 vs DB·임베딩 방식

## 전제

이 문서는 `problem.md`와 `지침재료/`를 근거로, 국회 요구자료 배분·회신·취합 지원 도구를 두 가지 버전으로 나누어 설계한다. 두 버전 모두 답변 작성, 결재, 국회 제출, 내부 시스템 실제 등록은 범위 밖으로 둔다. AI는 문항 분해, 소관 과 후보 추천, 누락 점검을 돕는 역할이며, 최종 배분과 확정은 국회 총괄 담당이 판단한다.

## 버전 A: 보관된 파일 직접 읽기 방식

### 개념

CSV, XLSX, JSON처럼 폴더에 보관된 파일을 서버가 직접 읽고 쓴다. 과거 접수대장은 읽기 전용으로 두고, 업무 중 바뀌는 문항 상태와 이력은 `cases.json`에 저장한다.

### 데이터 구성

| 데이터 | 용도 | 읽기/쓰기 |
|---|---|---|
| `data/요구자료_접수대장_2026국감_520건.csv` | 과거 접수대장 원본, 초기 문항 목록 | 읽기만 |
| `data/배분기준표_소관키워드_304건.csv` | 키워드 기반 소관 과 후보 추천 | 읽기만 |
| `data/A부_조직도_26개과.csv` | 배분 가능한 과 목록 검증 | 읽기만 |
| `data/시험_요구문항_40건.csv` | 1순위 배분 정확도 검증 | 읽기만 |
| `cases.json` | 문항별 상태, 배분, 회신, 요청, 이력 | 읽기/쓰기 |

### 처리 흐름

| 단계 | 처리 |
|---|---|
| 접수 | 접수대장 CSV 520건을 읽어 화면 목록을 만든다. |
| 분해 | CSV의 접수번호와 문항번호를 기준으로 문항 단위 `caseId`를 만든다. |
| 배분 추천 | 요구내용과 배분기준표 키워드를 비교해 후보 과를 계산한다. |
| 배분 확정 | 총괄 담당이 후보를 보고 `cases.json`에 확정 과와 이력을 저장한다. |
| 회신 | 현업 담당이 회신 내용을 저장하고 상태를 `회신완료`로 바꾼다. |
| 검사 | `cases.json`과 원본 CSV를 비교해 누락, 상태, 부서명, 기한 이상을 점검한다. |
| 확정 | 총괄 담당이 확인 후 상태를 `확정`으로 바꾼다. |

### API 설계

기존 `design.md`처럼 `/api/app` 하나만 사용한다. 서버 내부 저장소가 파일이라는 점만 다르다.

```json
{
  "action": "AI추천",
  "payload": {
    "caseId": "2026-0001-01"
  }
}
```

응답은 키워드 매칭 결과와 사람이 확인해야 하는 이유를 반환한다.

```json
{
  "ok": true,
  "caseId": "2026-0001-01",
  "recommendation": {
    "dept": "운영지원과",
    "keywords": ["업무추진비", "집행"],
    "needsHumanReview": true,
    "reason": "공통 문항 가능성이 있어 주관 과 확인 필요"
  }
}
```

### 장점

| 항목 | 내용 |
|---|---|
| 빠른 시작 | 현재 폴더의 CSV와 JSON만으로 만들 수 있다. |
| 설명 가능성 | 어떤 파일을 읽고 어떤 값이 바뀌었는지 확인하기 쉽다. |
| 교육 실습 적합성 | 520건 규모와 시험 40건 검증에는 충분하다. |
| 운영 부담 | 별도 DB 설치나 색인 관리가 필요 없다. |

### 단점

| 항목 | 내용 |
|---|---|
| 동시 작업 취약 | 여러 명이 동시에 저장하면 충돌 처리가 어렵다. |
| 검색 한계 | 의미가 비슷한 문항 찾기는 키워드 규칙에 의존한다. |
| 이력 확장 한계 | 이력이 많아질수록 JSON 파일 관리가 무거워진다. |
| 권한 관리 한계 | 과별 권한, 감사 로그, 장기 보관 기능은 별도 구현이 필요하다. |

### 적합한 경우

S3~S8 실습을 빠르게 완주하고, 배분 추천 정확도 75% 이상을 확인하는 것이 목표일 때 적합하다. 현재 자료 규모에서는 이 방식이 1차 구현에 가장 안전하다.

## 버전 B: DB + 임베딩 검색 방식

### 개념

접수대장, 배분기준표, 조직도, 지침재료를 DB에 넣고, 요구내용·키워드·지침 문장을 임베딩해 의미 기반 검색을 함께 사용한다. MongoDB를 쓴다면 문항 상태와 업무 이력은 일반 문서로 저장하고, 벡터 검색은 별도 벡터 인덱스 또는 벡터 DB에 둔다. 전용 벡터 DB를 쓴다면 업무 상태는 별도 DB에, 의미 검색용 벡터는 벡터 DB에 저장한다.

### 데이터 구성

| 저장소 | 컬렉션/테이블 | 용도 |
|---|---|---|
| 업무 DB | `cases` | 문항별 상태, 배분, 회신, 요청, 확정 여부 |
| 업무 DB | `history` | 누가 언제 무엇을 왜 바꿨는지 기록 |
| 업무 DB | `departments` | 조직도 26개 과와 주요업무 |
| 업무 DB | `rules` | 배분기준표 304건 |
| 업무 DB | `source_rows` | 과거 접수대장 520건의 원본 보존본 |
| 벡터 인덱스 | `embeddings` | 요구내용, 기준표 키워드, 조직도 주요업무, 지침 문장 임베딩 |

### 처리 흐름

| 단계 | 처리 |
|---|---|
| 적재 | CSV와 지침재료를 DB에 넣고 검색용 텍스트를 만든다. |
| 임베딩 | 요구내용, 대표키워드, 주요업무, 배분 규칙, 지침 문장을 임베딩한다. |
| 접수 | `source_rows`에서 문항을 불러와 `cases`에 상태를 만든다. |
| AI추천 | 키워드 규칙 점수와 벡터 유사도 점수를 함께 계산한다. |
| 배분 확정 | 총괄 담당의 결정을 `cases`에 저장하고 `history`에 기록한다. |
| 회신 | 현업 담당 회신과 재배정요청을 DB에 저장한다. |
| 검사 | DB 쿼리와 규칙 검사를 함께 수행한다. 필요하면 유사 과거 사례를 검색한다. |
| 확정 | 확정 상태와 확정 사유를 남긴다. |

### 추천 로직

| 요소 | 설명 |
|---|---|
| 키워드 점수 | 배분기준표의 키워드, 제외어, 우선순위를 반영한다. |
| 조직도 점수 | 조직도 주요업무·대표키워드와 요구내용의 유사도를 본다. |
| 과거 사례 점수 | 비슷한 과거 문항이 어느 과로 배분됐는지 참고한다. |
| 지침 점수 | 지침재료의 최신 기준, 공통 문항 처리, 재배정 원칙을 참고한다. |
| 확인필요 조건 | 기준표 미매칭, 우선순위 동률, 조직도 밖 과, 공통 문항 가능성은 사람이 확인한다. |

### API 설계

외부 모양은 `/api/app` 하나로 유지한다. 내부에서 DB 조회와 벡터 검색을 함께 수행한다.

```json
{
  "action": "AI추천",
  "payload": {
    "caseId": "2026-0001-01",
    "useSemanticSearch": true
  }
}
```

응답은 규칙 기반 근거와 의미 검색 근거를 나누어 보여 준다.

```json
{
  "ok": true,
  "caseId": "2026-0001-01",
  "recommendation": {
    "dept": "운영지원과",
    "score": 0.86,
    "ruleEvidence": {
      "matchedKeywords": ["업무추진비", "집행"],
      "priority": 90
    },
    "semanticEvidence": [
      {
        "source": "조직도",
        "text": "예산 집행, 회계, 서무",
        "similarity": 0.81
      },
      {
        "source": "지침재료",
        "text": "업무추진비 문항은 주관 과가 전 과 회신을 받아 합친다.",
        "similarity": 0.78
      }
    ],
    "needsHumanReview": true,
    "reason": "공통 문항 가능성이 있어 주관 과 확정 필요"
  }
}
```

### 장점

| 항목 | 내용 |
|---|---|
| 의미 검색 | 표현이 달라도 비슷한 문항과 소관 과를 찾기 쉽다. |
| 확장성 | 자료가 여러 해로 늘어나거나 문항이 많아져도 구조적으로 관리하기 좋다. |
| 동시 작업 | 여러 담당자가 함께 써도 상태 저장과 이력 관리가 안정적이다. |
| 감사 추적 | 누가 언제 배분·회신·확정했는지 기록하기 쉽다. |
| 재사용 | 과거 사례 검색, 유사 문항 추천, 지침 근거 제시에 유리하다. |

### 단점

| 항목 | 내용 |
|---|---|
| 초기 복잡도 | DB 설치, 스키마 설계, 임베딩 적재, 인덱스 관리가 필요하다. |
| 운영 부담 | 백업, 권한, 장애 대응, 색인 재생성 절차가 필요하다. |
| 설명 관리 | 벡터 유사도만으로는 왜 추천됐는지 부족하므로 규칙 근거를 함께 보여 줘야 한다. |
| 보안 검토 | 실제 요구자료를 넣는다면 개인정보와 내부자료 반출 기준을 더 엄격히 봐야 한다. |

### 적합한 경우

여러 연도 자료를 누적하고, 유사 사례 검색과 지침 근거 검색까지 업무 기능으로 만들 때 적합하다. 실습을 넘어 실제 팀 단위 도구로 키울 계획이 있으면 이 방식이 낫다.

## 두 버전 비교

| 비교 항목 | 버전 A: 파일 직접 읽기 | 버전 B: DB + 임베딩 |
|---|---|---|
| 시작 속도 | 빠름 | 느림 |
| 구현 난이도 | 낮음 | 높음 |
| 현재 520건 처리 | 충분함 | 충분함 |
| 시험 40건 정확도 검증 | 가능 | 가능 |
| 키워드 규칙 반영 | 좋음 | 좋음 |
| 비슷한 표현 검색 | 약함 | 강함 |
| 여러 명 동시 작업 | 약함 | 강함 |
| 이력 관리 | 가능하지만 단순함 | 체계적 |
| 운영 부담 | 낮음 | 높음 |
| 보안 관리 | 파일 권한 중심 | DB 권한·백업·접근통제 필요 |
| 설명 가능성 | 높음 | 규칙 근거를 함께 보여 줘야 높아짐 |
| 실습 적합성 | 매우 높음 | 과할 수 있음 |
| 실제 업무 확장성 | 보통 | 높음 |

## 실제 회사 자료 11~20GB 기준 보완

사용자가 붙일 실제 회사 자료가 약 11GB이고 ZIP까지 포함하면 약 20GB까지 커질 수 있다면, 현재 설계의 전제는 실습용 520건보다 훨씬 커진다. 이 경우 파일 직접 읽기 방식은 전체 구현 방식이 아니라 "초기 검증용"으로만 보는 것이 안전하다.

### 큰 자료에서 피해야 할 방식

| 피할 방식 | 이유 |
|---|---|
| 요청 때마다 ZIP을 풀고 전체 파일을 훑기 | 응답 시간이 길고, 같은 작업을 반복하며, 파일 손상이나 중간 실패에 취약하다. |
| 원본 파일 전체를 DB에 그대로 넣기 | DB 용량과 백업 부담이 커지고, HWPX·PDF·XLSX 같은 원본 문서 보관에 적합하지 않다. |
| 모든 문서를 한 번에 임베딩하기 | 비용과 시간이 커지고, 개인정보·내부자료가 섞였을 때 통제가 어렵다. |
| 벡터 유사도만으로 배분 확정하기 | 왜 그 과인지 설명하기 어렵고, 최종 판단은 사람이 해야 한다는 지침과 맞지 않는다. |

### 권장 구조: 원본 보관소 + 메타데이터 DB + 검색 인덱스

| 층 | 역할 | 저장 내용 |
|---|---|---|
| 원본 보관소 | 회사 자료 원본 보존 | ZIP, HWPX, HWP, PDF, XLSX, CSV 등 원본 파일 |
| 추출 텍스트 보관 | 검색과 요약에 쓸 텍스트 | 파일별 추출 텍스트, 페이지/시트/문단 단위 텍스트 |
| 업무 DB | 상태와 이력 관리 | cases, history, departments, rules, source_rows, file_index |
| 검색 인덱스 | 빠른 키워드 검색 | 접수번호, 의원명, 위원회, 부서명, 키워드, 날짜 |
| 벡터 인덱스 | 의미 기반 검색 | 요구내용, 지침 문장, 조직도 주요업무, 과거 유사 문항 임베딩 |

이 구조에서는 원본 파일을 직접 수정하지 않는다. 서버는 먼저 DB와 인덱스를 조회하고, 사용자가 근거를 확인할 때만 원본 파일의 해당 위치를 열어 보여 준다.

### 수집·색인 흐름

| 단계 | 처리 | 결과 |
|---|---|---|
| 1. 파일 등록 | 회사 자료 폴더나 ZIP을 등록한다. | 파일 목록, 크기, 수정일, 해시 |
| 2. 원본 보관 | ZIP은 보관하고, 필요한 경우 작업용 폴더에 한 번만 푼다. | 원본 경로와 압축 해제 경로 |
| 3. 텍스트 추출 | PDF, HWPX, XLSX, CSV 등에서 텍스트와 표를 추출한다. | 문서별 추출 텍스트 |
| 4. 메타데이터 생성 | 접수번호, 위원회, 의원명, 부서명, 날짜, 문항번호 후보를 뽑는다. | `file_index`, `source_rows` |
| 5. 규칙 색인 | 배분기준표, 조직도, 지침재료를 구조화한다. | `rules`, `departments`, `guidelines` |
| 6. 임베딩 | 필요한 텍스트 조각만 임베딩한다. | 벡터 인덱스 |
| 7. 검수 | 임베딩 제외 대상, 개인정보 포함 가능 문서, 추출 실패 문서를 확인한다. | 확인필요 목록 |

### 보안 기준

| 항목 | 기준 |
|---|---|
| 내부자료 | 실제 회사 자료는 내부 저장소에 두고, 외부 서비스 전송 여부를 별도 승인 대상으로 둔다. |
| 개인정보 | 성명, 연락처, 주민등록번호 등 개인정보 가능성이 있는 문서는 임베딩 전 마스킹 또는 제외한다. |
| 접근 권한 | 총괄 담당과 현업 담당의 조회 범위를 분리한다. 현업 담당은 자기 과 문항 중심으로 본다. |
| 이력 | 파일 등록, 추출, 검색, 배분, 회신, 확정 이력을 남긴다. |
| 원본 보존 | 원본 파일은 읽기 전용으로 두고, 추출본과 상태값만 별도로 갱신한다. |

### 11~20GB 기준 비교

| 비교 항목 | 파일 직접 읽기 | DB + 임베딩 | 권장 혼합안 |
|---|---|---|---|
| 11~20GB 원본 처리 | 느리고 불안정 | 가능하지만 설계 필요 | 원본은 파일 보관소, 색인은 DB |
| 최초 구축 | 빠름 | 느림 | 중간 |
| 반복 조회 | 느림 | 빠름 | 빠름 |
| 원본 보존 | 쉬움 | DB에 넣으면 부담 | 파일로 보존 |
| 상태·이력 | 약함 | 강함 | DB에서 관리 |
| 의미 검색 | 약함 | 강함 | 필요한 문서만 임베딩 |
| 보안 통제 | 폴더 권한 중심 | 세밀함 | 원본·색인 권한 분리 |
| 추천 | 프로토타입 | 운영형 | 운영 전환형 |

## 권장안

| 시점 | 권장 방식 | 이유 |
|---|---|---|
| 실습·검증 | 버전 A: 파일 직접 읽기 | 현재 교육용 자료 520건과 시험 40건으로 업무 흐름과 정확도를 빠르게 확인한다. |
| 회사 자료 준비 | 혼합안: 원본 보관소 + 메타데이터 DB | 11~20GB 원본은 파일로 보존하고, 목록·상태·이력·검색용 텍스트만 DB화한다. |
| 실제 운영 | 혼합안 + 선택적 임베딩 | 전체를 무작정 임베딩하지 않고, 요구내용·지침·조직도·과거 문항처럼 추천에 필요한 텍스트만 임베딩한다. |
| 장기 확장 | DB + 벡터 인덱스 | 여러 해 자료, 여러 담당자, 유사 사례 검색, 감사 이력이 중요해지면 운영형 구조로 전환한다. |

## 최종 제안

우선 S3~S8은 교육용 자료로 버전 A를 사용해 빠르게 검증한다. 다만 실제 회사 자료가 11~20GB라면 운영 설계는 처음부터 혼합안으로 잡는다. 원본은 파일 보관소에 두고, 서버는 메타데이터 DB와 검색 인덱스를 먼저 보며, 임베딩은 추천에 필요한 텍스트 조각에만 적용한다.

이렇게 하면 실습은 가볍게 진행하면서도, 회사 자료를 붙일 때 전체 파일을 매번 읽거나 전체 원본을 DB에 밀어 넣는 위험을 피할 수 있다.
