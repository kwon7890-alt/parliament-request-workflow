# 설계서: 국회 요구자료 배분·회신·취합 지원 도구

## 1. 업무 흐름과 사람 확인 지점

| 흐름 | 국회 총괄 담당(배분·취합) | 현업 담당(과) | 시스템이 돕는 일 | 사람 확인 지점 |
|---|---|---|---|---|
| 접수 | 요구서를 접수하고 접수번호, 접수일, 위원회, 의원, 제출기한 등을 확인한다. | 해당 없음 | 과거 접수대장을 읽어 기본 항목을 화면에 보여 준다. | 제출기한이 접수일보다 빠르거나 날짜가 이상한 경우 총괄 담당이 의원실 확인 여부를 판단한다. |
| 분해 | 요구서를 문항 단위로 나누고 문항번호와 요구내용을 정리한다. | 해당 없음 | 문항 단위 처리 목록을 만들고 개인정보, 기간, 중복 의심 등 확인 항목을 표시한다. | 하위 항목을 별도 문항으로 볼지, 같은 문항으로 묶을지 총괄 담당이 확정한다. |
| 배분 | 배분기준표와 조직도를 보고 주관 과와 협조 과를 정한다. | 배분 결과를 확인하고 이견이 있으면 재배정요청을 보낸다. | AI추천으로 소관 과 후보, 근거 키워드, 확인필요 사유를 제시한다. | 최종 배분은 총괄 담당이 확정한다. 기준표 미매칭, 우선순위 동률, 여러 과 관련 문항은 임의 확정하지 않는다. |
| 부서 회신 | 배분 확정 문항을 과별로 보낸 뒤 회신 현황을 본다. | 자기 과 문항에 답변 초안과 근거 자료를 입력하고 회신완료 처리한다. | 과별 할 일, 제출기한, 회신 상태, 보완요청 여부를 보여 준다. | 답변 내용의 사실관계와 근거 자료는 현업 담당이 책임지고 확인한다. |
| 검사 | 회신 자료를 모아 누락, 기간 오류, 조직도 외 부서명, 합계 불일치 등을 점검한다. | 보완요청을 받으면 회신 내용을 보완한다. | 검사 결과를 정상, 확인필요, 보완요청 후보로 나눠 보여 준다. | 이상 항목을 실제 오류로 볼지, 보완요청할지 총괄 담당이 판단한다. |
| 확정 | 회신이 충분한 문항을 확정 처리한다. | 보완이 끝난 문항을 다시 회신완료 처리한다. | 상태를 확정으로 바꾸고 처리 이력을 남긴다. | 최종 확정은 총괄 담당이 한다. 답변·결재·제출 여부는 이 도구가 자동 결정하지 않는다. |
| 제출본 | 결재와 제출을 위한 제출본 대상을 확인한다. | 필요 시 최종 보완에 응한다. | 확정된 문항 목록과 미확정 사유를 보여 준다. | 결재, 국회 제출, 수정 제출은 범위 밖이며 사람이 별도 절차로 처리한다. |

상태 흐름은 `접수 → 배분확정 → 회신중 → 회신완료 → 확정`을 기본으로 한다. 예외 상태로 `재배정요청`, `보완요청`을 둔다.

## 2. 업무 화면

| 화면 | 누가 쓰는지 | 보이는 정보 | 버튼 | 왜 필요한지 |
|---|---|---|---|---|
| 시작 화면(현황) | 국회 총괄 담당, 현업 담당 | 전체 건수, 상태별 건수, 제출기한 임박 건, 재배정요청 건, 보완요청 건, 과별 회신 현황 | 새로고침, 상태 필터, 내 과만 보기, 상세 보기 | 담당자가 오늘 먼저 볼 일을 빠르게 정하고, 미회신 과를 매일 확인할 수 있게 한다. |
| 배분 화면 | 국회 총괄 담당 | 접수번호, 문항번호, 요구내용, 요구기간, 제출기한, 제출형식, AI추천 과, 추천 근거 키워드, 확인필요 사유, 현재 배분과 | AI추천, 배분확정, 확인필요 표시, 재배정 반영, 이력 보기 | 문항별 소관 과 후보를 보되 최종 배분은 사람이 확정하도록 하기 위해 필요하다. |
| 현업 회신 화면 | 현업 담당(과) | 내 과 배분 문항, 요구내용, 제출기한, 회신 양식 항목, 보완요청 사유, 처리 이력 | 회신 저장, 회신완료, 재배정요청, 보완 답변 저장 | 각 과가 자기 소관 문항만 보고 회신하며, “우리 과 아님” 이견을 이력으로 남기기 위해 필요하다. |
| 취합 화면 | 국회 총괄 담당 | 문항별 회신 상태, 미회신 과, 보완요청 대상, 검사 결과, 확정 가능 여부, 처리 이력 | 검사 실행, 보완요청, 확정, 제출본 대상 보기, 이력 보기 | 회신을 모아 누락·오류를 확인하고 제출 전 사람이 판단할 항목을 분리하기 위해 필요하다. |

## 3. 데이터

| 데이터 | 역할 | 저장 방식 | 주요 필드 | 규칙 |
|---|---|---|---|---|
| 과거 접수대장 | 2026년 국정감사 요구자료 520건의 원본 기준 자료 | 읽기만 사용 | 접수번호, 접수일, 국회구분, 위원회, 요구의원, 요구유형, 문항번호, 요구내용, 요구기간_시작, 요구기간_끝, 제출기한, 제출형식, 배분구분, 배분과, 처리상태 | 원본 행과 값은 수정하지 않는다. 화면 조회와 초기 cases 생성의 기준으로만 쓴다. |

## 4. 서버 API: `/api/app`

서버는 `/api/app` 하나만 둔다. `GET`은 조회, `POST`는 작업 실행에 사용한다.

### GET 조회

요청 예시:

```http
GET /api/app?view=dashboard&role=총괄
```

응답 예시:

```json
{
  "ok": true,
  "view": "dashboard",
  "summary": {
    "total": 520,
    "접수": 120,
    "배분확정": 140,
    "회신중": 130,
    "회신완료": 90,
    "확정": 40,
    "재배정요청": 8,
    "보완요청": 12
  },
  "items": [
    {
      "caseId": "2026-0001-01",
      "접수번호": "2026-0001",
      "문항번호": "1",
      "요구내용": "최근 3년간 업무추진비 집행 현황",
      "제출기한": "2026-09-06",
      "status": "회신중",
      "assignedDept": "운영지원과"
    }
  ]
}
```

### POST 접수

요청 예시:

```json
{
  "action": "접수",
  "actor": "국회 총괄 담당",
  "payload": {
    "source": "과거 접수대장",
    "접수번호": "2026-0001",
    "문항번호": "1"
  }
}
```

응답 예시:

```json
{
  "ok": true,
  "caseId": "2026-0001-01",
  "status": "접수",
  "message": "문항을 접수 상태로 생성했습니다."
}
```

### POST AI추천

요청 예시:

```json
{
  "action": "AI추천",
  "actor": "국회 총괄 담당",
  "payload": {
    "caseId": "2026-0001-01",
    "요구내용": "최근 3년간 업무추진비 집행 현황"
  }
}
```

응답 예시:

```json
{
  "ok": true,
  "caseId": "2026-0001-01",
  "recommendation": {
    "dept": "운영지원과",
    "score": 0.82,
    "keywords": ["업무추진비", "집행"],
    "needsHumanReview": true,
    "reason": "공통 문항 가능성이 있어 주관 과 확정 필요"
  }
}
```

## 5. 처리 위치 구분

| 구분 | 처리할 것 |
|---|---|
| 화면에서 처리할 것 | 상태별 목록 보기, 필터, 검색, 상세 확인, 버튼 클릭, 회신 입력, 재배정요청 사유 입력, 보완요청 사유 입력, 사람이 판단해야 하는 확인필요 표시 확인 |
| 서버에서 처리할 것 | 과거 접수대장 읽기, cases.json 조회·저장, 상태 변경 검증, 처리 이력 추가, AI추천 결과 저장, 배분과가 조직도 안에 있는지 확인, 누락·이상 항목 검사 |
| 하지 않을 것 | 답변 문장 자동 작성, 결재 자동 처리, 국회 제출 자동 처리, 내부 시스템 실제 등록, 개인정보가 포함된 실제 요구자료 외부 전송, 원본 접수대장 수정 |

## 6. 단계 S3~S8 연결

| 단계 | 만들 것 | 산출물 | 확인 기준 |
|---|---|---|---|
| S3 | 접수대장과 지침을 기준으로 화면·데이터·API 설계 확정 | `design.md` | 업무 흐름, 사람 확인 지점, 화면 4개, 데이터 2개, `/api/app` 예시가 들어 있다. |
| S4 | 과거 접수대장을 읽어 문항별 초기 cases 구조를 만든다. | `cases.json` 초기 데이터 | 접수대장 원본 520건을 수정하지 않고 문항 상태가 `접수`로 생성된다. |
| S5 | 배분 화면과 AI추천 작업을 만든다. | 배분 화면, `AI추천`, `배분` 작업 | 추천은 후보만 제시하고 최종 배분은 총괄 담당이 확정한다. |
| S6 | 현업 회신 화면과 회신·재배정요청 작업을 만든다. | 현업 회신 화면, `회신`, `재배정요청` 작업 | 현업 담당은 내 과 문항만 보고 회신하거나 재배정요청을 남길 수 있다. |
| S7 | 취합 화면과 검사·보완요청·확정 작업을 만든다. | 취합 화면, `보완요청`, `확정` 작업 | 누락·오류 후보가 확인필요로 표시되고, 확정은 총괄 담당이 실행한다. |
| S8 | 검증 자료로 정확도와 흐름을 확인한다. | 검증 결과 기록 | 시험 40건 기준 1순위 배분과 정확도 75% 이상, 조직도 밖 배분과 생성 없음, 답변·결재·제출은 제외된다. |
