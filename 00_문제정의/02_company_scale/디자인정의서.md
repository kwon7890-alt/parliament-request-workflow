# 디자인정의서: 국회 요구자료 대응 도우미 회사용 확장

> 버전: `02_company_scale`  
> 원칙: 원본 보존, 내부망 처리, 변경분 갱신, 출처 표시, 선택적 임베딩

## 1. 구조

```text
원본 보관소(raw_vault)
        ↓ 안전 수집·해시·형식 판별
추출 저장소(extracted) ── 메타데이터 DB
        ↓                    ├─ 파일·버전·권한
키워드 검색 인덱스          ├─ 문항·상태·이력
        ↓                    └─ 민감정보 검토
선택적 벡터 인덱스
        ↓
현황·배분·현업 회신·취합·수집관리 화면
```

DB는 특정 제품을 먼저 고르지 않는다. 파일·문항·이력·권한처럼 관계와 감사가 중요한 데이터는 메타데이터 DB에 저장하고, 검색은 별도 검색 인덱스, 의미 검색은 벡터 인덱스로 분리한다. MongoDB 한 제품에 전부 넣거나 벡터DB 하나로 원본을 대체하지 않는다.

## 2. 수집 대상 분류

| 분류 | 예시 | 처리 |
|---|---|---|
| A. 국회 업무 핵심 | 요구서, 접수대장, 배분기준표, 조직도, 지침, 회신, 답변·결재 양식 | 추출·키워드 색인, 승인 조각 선택 임베딩 |
| B. 공유 업무 자료 | 예산·결산 등 다른 업무에서도 쓰는 승인 자료 | C1에서 공용 수집층 사용 여부와 권한을 정한 뒤 처리 |
| C. 목록 관리 | 설치 매뉴얼, 교육자료, 과업지시서 등 국회 업무 관련성이 낮은 자료 | 기본은 파일 정보와 해시만 기록, 별도 승인 시 색인 |
| D. 제외·위험 | 설치파일, 실행 스크립트, 레지스트리, 반입 금지 자료 | 내용 색인·실행 금지, 정책에 따라 목록만 기록하거나 제외 |

분류가 확정되지 않은 자료는 색인하지 않는다. C1에서 분류 책임자, 재분류 승인 절차, 예산 RAG와 공용 수집층을 사용할지를 결정한다.

## 3. 수집 흐름

| 단계 | 처리 | 사람 확인 |
|---|---|---|
| 등록 | 폴더·ZIP을 등록하고 수집 단위를 만든다 | 반입 가능 여부와 A~D 분류 |
| 목록화 | 경로, 크기, 수정일, 확장자, 해시 기록 | 접근 권한과 보존 등급 |
| 분류 | 문서·압축·위험·미지원 파일 분류 | 위험·미지원 파일 처리 |
| 추출 | 텍스트·표·페이지·시트·문단 위치 추출 | 추출 실패와 깨진 문서 |
| 민감정보 검사 | 연락처·이메일·키 후보·보안정보 후보 표시 | 마스킹·제외·승인 |
| 색인 | 승인된 텍스트를 키워드 색인 | 색인 대상 범위 |
| 선택 임베딩 | 지침·조직도·과거 문항·회신 등 필요한 조각만 임베딩 | 민감 자료 포함 여부 |
| 갱신 | 해시·수정일 변화가 있는 파일만 재처리 | 삭제·이동 정책 |

## 4. 저장소

| 저장소 | 내용 | 원칙 |
|---|---|---|
| `raw_vault` | 원본 파일 | 읽기 전용, 직접 수정 금지 |
| `extracted` | 추출 텍스트·표·위치 정보 | 원본 해시와 연결 |
| `files` | 경로, 해시, 크기, 형식, 버전, 등급, 처리상태 | 하나의 파일 식별자 사용 |
| `documents` | 문서 유형, 작성일, 시행일, 최신 여부 | 최신 지침 판별 근거 |
| `cases` | 문항, 배분, 상태, 회신, 검사 | PoC 상태 개념 계승 |
| `history` | 사용자, 작업, 시각, 사유, 전·후 위치와 조치 | 보존기간 동안 추가형 기록. 개인정보 원문 값은 저장하지 않음 |
| `permissions` | 사용자·역할·자료 등급 | 최소 권한 |
| `sensitive_findings` | 민감정보 후보, 위치, 처리결과 | 승인 전 검색·임베딩 차단 |
| `search_index` | 키워드·필터 검색 | 전체 승인 텍스트 대상 |
| `vector_index` | 선택된 텍스트 조각의 임베딩 | 원문·출처와 임베딩 모델명·버전·차원·분할 규칙·색인 버전·원문 해시 연결 |

## 5. 파일 정책

| 형식 | 처리 |
|---|---|
| PDF | 페이지별 추출, 스캔본은 승인된 OCR 사용 |
| HWPX·DOCX | 문단·표와 위치 추출 |
| HWP | C2에서 파일 비율·용량을 측정하고 C4 전에 내부 변환 서버 등 처리 방식을 확정 |
| XLSX·CSV | 시트·열·행 구조 보존, 대형 시트 분할 |
| HTML·TXT | 실행 없이 본문 추출, 인코딩 기록 |
| ZIP | 내부 목록과 해시 확인 후 격리 위치에 한 번만 해제. 중첩 깊이 기본 2단계까지 자동 처리 |
| EXE·BAT·REG | 실행 금지, 해시·크기·경로만 기록하고 위험 표시 |

암호화 ZIP과 손상 파일은 자동 처리를 멈춘다. 중첩 깊이가 2단계를 넘거나, C2에서 정하고 보안 담당자가 승인한 압축 해제 비율·파일 수·개별 파일 크기 한도를 넘을 때만 검토 대상으로 보낸다. 정상적인 자료요청 ZIP 안의 HWP는 허용 범위에서 자동 처리한다.

| 화면 | 사용자 | 핵심 정보·기능 |
|---|---|---|
| 현황 | 총괄·현업 | 업무 상태, 기한, 과별 진행, 검색 바로가기 |
| 배분 | 총괄 | 후보 3순위, 기준표·조직도·과거사례 출처, 확정·재배정 |
| 현업 회신 | 현업 | 내 과 문항, 근거 자료 검색, 회신·재배정·보완 |
| 취합 | 총괄 | 미회신, 검사, 보완, 확정, 처리 이력 |
| 수집·색인 관리 | 관리자 | 등록 파일 수·용량, 중복, 실패, 위험, 민감정보, 색인 버전 |
| 검색 | 권한 사용자 | 키워드·기간·문서유형·부서 필터, 원문 위치, 최신 지침 표시 |

## 7. 검색·추천

1. 키워드 검색으로 후보 문서를 좁힌다.
2. 권한과 민감정보 승인 여부를 적용한다.
3. 필요한 경우에만 벡터 유사도로 재정렬한다.
4. 배분기준표·조직도·최신 지침·과거 확정 사례의 점수를 구분해 보여 준다.
5. 결과마다 파일명, 문서 버전, 페이지·시트·문단, 원문 열기 정보를 표시한다.
6. 추천은 업무 지침 변경이 아니라 의사결정 보조이며 최종 배분은 총괄 담당이 확정한다.

## 8. 상태와 API

업무 상태는 `접수 → 배분확정 → 회신중 → 회신완료 → 확정`, 예외는 `재배정요청`, `보완요청`, `중복`이다. `확인필요`는 별도 표시다.

외부 화면은 `/api/app`을 유지하되 서버 내부 기능을 나눈다.

| 작업 | 예시 값 |
|---|---|
| 업무 | 접수, AI추천, 배분, 회신, 재배정요청, 보완요청, 확정 |
| 수집 | 수집등록, 목록화, 텍스트추출, 민감정보검토 |
| 색인 | 키워드색인, 선택임베딩, 증분갱신 |
| 운영 | 실패재처리, 접근이력조회, 색인버전전환 |

```json
{
  "action": "수집등록",
  "actor": "시스템 관리자",
  "payload": {"sourceId": "SRC-2026-001", "mode": "incremental"}
}
```

```json
{
  "ok": true,
  "jobId": "JOB-001",
  "status": "검토대기",
  "summary": {"new": 0, "changed": 0, "duplicate": 0, "risky": 0}
}
```

숫자 0은 응답 구조 예시이며 실제 처리량 추정치가 아니다.

## 9. 보안과 운영 통제

| 통제 | 내용 |
|---|---|
| 내부망 | 원본·추출문·임베딩을 외부 서비스로 전송하지 않음 |
| 승인 관문 | 민감정보 검토 전 검색·임베딩 제외 |
| 최소 권한 | 사용자 역할과 자료 등급에 따라 원문·검색 결과 제한 |
| 비밀정보 | API 키 후보는 값 자체를 로그에 남기지 않고 위치와 조치만 기록 |
| 감사 | 조회·다운로드·변경·삭제·권한 변경 이력 기록. 개인정보 원문 값은 남기지 않고 위치·유형·조치만 기록 |
| 보존·파기 | 보존기간 동안 이력을 추가형으로 유지하고, 기간 만료 시 승인된 파기·익명화 절차와 파기 사실을 별도 기록 |
| 복구 | DB·색인과 원본의 백업·복원 절차 분리 |
| 색인 버전 | 새 색인을 검증한 뒤 전환하고 이전 버전으로 되돌릴 수 있게 함. 서버 이전 또는 임베딩 모델·버전·차원 변경 시 승인 자료를 재임베딩하고 전환 전후 결과를 비교 |

내부망 AI 서버를 L40S에서 RTX PRO 6000 환경으로 옮길 때도 같은 절차를 적용한다. 장비만 바뀌고 모델·토크나이저·차원·분할 규칙이 같으면 재현성 검사를 먼저 하고, 어느 하나라도 바뀌면 새 색인 버전으로 전체 승인 조각을 재임베딩한다.

## 10. 구축 순서

| 단계 | 산출물 | 완료 기준 |
|---|---|---|
| C1 | 자료 분류·보안 기준 | A~D 수집 분류, 공용 수집층 여부, 반입·권한·보존·파기 승인 |
| C2 | 파일 목록·해시 조사 | 파일 수·용량·형식·중복, HWP 비율, ZIP 깊이·해제 비율 기준선 확보 |
| C3 | 원본 보관소·메타데이터 DB | 원본 수정 없이 파일 식별·버전 관리 |
| C4 | 추출·민감정보 관문 | HWP 처리 방식 확정, 지원 형식 추출, 가상 표본 탐지율 100%, 승인 전 차단 |
| C5 | 키워드 검색 | 원문 위치와 권한이 맞는 결과 제공 |
| C6 | 선택 임베딩 | 승인 조각만 의미 검색, 출처 100% 연결 |
| C7 | 업무 화면 연계 | 배분·회신·취합에서 근거 검색 사용 |
| C8 | 운영 검증 | 증분 처리·복구·권한·성능·감사·파기·서버 이전 재임베딩 통과 |

PoC를 복사해 이름만 바꾸지 않는다. 회사용은 C1~C2 조사 결과를 바탕으로 저장 제품과 장비별 성능 목표를 확정한다.
